# AIエージェントで業務を変えよう！ Section 2
## AIエージェント入門

### AIエージェントとは

#### 仕事の本質：判断と実行の連続

AIエージェントとは何かを理解するために、まずは簡単な例をもとに、私たちがどのように仕事を行っているのか、そしてその仕事をどのようにAI化できるのかを考えてみましょう。

**基本的な例：犬と猫の写真分類**

私たちが行う仕事というのは、判断と実行の連続で成り立っています。

皆さんの手元に犬と猫の写真がたくさんあり、それらを犬のフォルダーと猫のフォルダーに分類するという仕事があったとします。

この仕事は、2つのタスクで構成されます：

| タスク | 説明 |
|--------|------|
| **判断タスク** | 目の前にある写真が犬なのか猫なのかを判断 |
| **実行タスク** | 判断結果をもとに写真をそれぞれのフォルダーに入れる |

#### 従来的なAIの能力

AI、すなわち機械学習技術を応用して、既存のデータから未知のデータを予測するシステムを活用することで、私たちの仕事のうち**判断の部分**を機械に行わせることができます。

つまり、AIに写真を見せれば、AIは過去に学習した犬と猫の特徴をもとに、その写真に写っているのが犬なのか猫なのかを判断することができます。

**しかし、純粋なAIの機能はここまでです。**

実際に写真を犬と猫のフォルダーに振り分ける実行の作業は、AIの結果を見ながら人間が行うことになります。

```
AIの能力：
写真を見る → 判断する（犬か猫か） → 出力
            ↓
        人間が結果を見て手動で分類
```

#### AIエージェントの新しい能力

**AIエージェント**はAIの判断結果を元に実行するところまでを自動化できるようにしたシステムです。

つまり、AIが写真を見て犬か猫かを判断したら、そのまま自動的にフォルダーへの振り分けまで行う。これがAIエージェントというシステムです。

```
AIエージェントの能力：
写真を見る → 判断する（犬か猫か） → 自動実行（フォルダ分類）
            ↓         ↓
        AI判断    従来的なシステムが実行
```

#### 重要なポイント：AIエージェントの構成

後半の実行部分、つまり写真をフォルダーに格納する部分はAIらしい要素はなく、**従来的なシステムの動作**です。

このように、AIエージェントというのは、全体がAIで構成されているのではなく、**AIと従来的なシステムが合体したような構造**になることもあります。

もしかすると、このようなシステムを既に導入しているという職場もあるかもしれません。以前からあるシステムだとしても、AIによる判断をもとに自動実行するシステムであれば、それはAIエージェントと呼んで差し支えないでしょう。

#### なぜ今、AIエージェントが注目されているのか

AIエージェントという言葉が今注目されているのは、その仕組み自体が新しいというよりは、**生成AIの登場によってAIに判断できる領域や自動実行できる領域が大きくなった**からだと考えることができます。

生成AIの登場により、業務への活用の可能性や業務プロセスを大きく変える可能性が広がったのです。

#### エージェント型AI：複数エージェントの統合

AIエージェントを発展させたシステムとして、**エージェント型AI**というものがあります。

これは、複数のAIエージェントを組み合わせることで、さらに複雑な仕事に対応できるシステムのことです。

**具体例：写真整理システムの拡張**

先ほどの犬と猫の写真を分類するAIエージェントの他に、収集した写真を使ってアルバムを作るAIエージェントを作ったとします。

すると、この2つのエージェントを組み合わせて写真を溜め込み、勝手にアルバムを作ってくれるAIシステムを構築することができそうです。

#### エージェント型AIの重要な特徴：自律的な判断

ここで大事なことは、**2つのAIエージェントを接続する仕組み**です。

従来でも一つの画面にAIエージェントを起動するボタンを配置して、それを人間が使い分けるというシステムは実装することができました。

しかし、今では**この人間との接点に生成AIを利用する**ことができます。

```
従来型：
人間 → どのエージェントを使う？ → エージェント1 or エージェント2

エージェント型AI：
人間 → 生成AI（判断） → 自動選択 → エージェント1 or エージェント2
```

つまり、人間がやりとりするのは生成AIで、その生成AIとの会話の内容に応じて実行するAIエージェントが自律的に判断される。

このような仕組みを作ることができます。

#### 外注の感覚で理解する

このように、生成AIが複数のAIエージェントを自律的に使い分ける。これがエージェント型AIの特徴です。

この考え方を応用すれば、業務振分けを行うエージェントにさまざまなエージェントやシステムをあらかじめ接続しておくことで、一つの大きなチームのような存在を作ることができます。

**従来的な仕事の分類方法：**

これまでは、仕事が与えられたら、人間がその仕事を小さいタスクに分解して、それぞれのタスクを適切なシステムで処理するということを行っていました。

**AIエージェント型の仕事の分類方法：**

一方で、AIエージェントは仕事を小さいタスクに分解するという作業や、一つ一つのタスクに適切なシステムを判断して処理するという作業を自律的に行うことができます。

**重要な認識：**

これは、外部の組織や取引先に仕事を外注するという感覚に似ています。

AIエージェントやエージェント型AIを活用することは、**AIのチームに仕事を外注することなのだ**と理解すると、新しい働き方のイメージを持ちやすくなるのではないでしょうか。

### AIエージェントによる業務自動化

#### 業務自動化の3つの手段

業務を自動化する手段を比較すると、以下の3つが大きく考えられます：

1. **従来型システム**を使う方法
2. **従来型AI**を組み込んだエージェント
3. **生成AI**を組み込んだエージェント

#### 手段1：従来型システム

```
特徴：
ルールベースの自動化
判断と実行は予め人間が決めたルールに基づく

メリット：
- 正確性が高い
- 予め決めた以外の動作をしない

デメリット：
- 柔軟性は低い
- 人間が担う領域が大きい
```

#### 手段2：従来型AIエージェント

```
特徴：
従来の機械学習やディープラーニングをもとに、
未知のデータを予測する機能を持つAI

メリット：
- 過去のデータをもとに柔軟な判断が可能
- 定型業務の精度が高い

デメリット：
- 正確性はルールベースより劣る
- インプット・アウトプットの種類や構造をあらかじめ定義が必要
- 制約が多い
```

#### 手段3：生成AIエージェント

```
特徴：
生成AIを活用したエージェント

メリット：
- インプット・アウトプットの制約を小さくできる
- 文章などの非構造化データを扱える
- 不定形なシステム操作が可能
- 従来の手法では難しかった業務に対応可能

デメリット：
- 判断や実行にあいまいさやばらつきが生じる
- 正確性は相対的に低い
```

#### 手段の選択：どれが最適か

それぞれの業務自動化手段は、ひと口にどれが最も優れていると言えるものではありません。

**しかし、重要なポイント：**

**AIエージェントを活用することで、今までは自動化が不可能だった領域での自動化が可能になるという点が非常に重要です。**

#### 営業プロセス自動化の具体例

営業における問い合わせから提案までのプロセスをどのように自動化するか考えてみます。

一般的な営業プロセス：問い合わせ → 担当者割り振り → 見積り作成 → 提案書作成 → 提案実施

##### 従来型システムでの自動化

```
実装内容：
1. WEBフォーム投稿がトリガー
2. 内容に応じて担当部署を自動割り振り
3. 部署にメール通知
4. CRM（顧客管理システム）にデータ入力

限界：ここまでが従来型システムの自動化範囲

その後は：
- 担当部署が問い合わせ内容を見ながら見積作成
- 提案書を手動作成
- 実際に顧客に提案（人間が実施）
```

##### 従来型AIエージェントでの自動化

```
追加機能：
問い合わせフォームの内容から過去の提案データをもとに
→ 今回の提案内容を判断
→ 見積金額を算出

システム構成：
- 担当部署割り振りシステム
- 見積金額計算AIエージェント

統合結果：
「見積もりエージェント」として機能
顧客フォーム投稿 → 担当部署割り振り → 見積作成 → CRMに記録
```

**注意点：** 担当部署の割り振りにAIを活用することは可能ですが、これはあまり良いアイデアではありません。多くの場合、顧客が入力した業界や関心製品によって部署は機械的に決められるはずですから、AIを使ってもメリットが特にないのです。

##### 生成AIエージェントでの自動化

```
重要な追加：提案書自動作成
提案書や トークスクリプト作成といったコンテンツを生み出す仕事を
AIが担えるようになることで、自動化可能な範囲が一気に広がります

システム構成：
- 見積りエージェント
- 提案作成エージェント
- 業務振分けエージェント（統括）

エージェント型AIの特徴：
営業担当者からの「やっぱり見積もりはこうして欲しい」
「提案書のこの部分を直して欲しい」といった要求に対して、
エージェントが臨機応変に連携
```

#### AIエージェント vs エージェント型AIの違い

| 判定ポイント | AIエージェント | エージェント型AI |
|------------|----------------|-----------------|
| **複数エージェントの接続** | 直列に繋ぐ（一方通行） | 統括エージェントで自律管理 |
| **対話性** | ワンショット（一度の実行） | 対話型（臨機応変な対応） |
| **柔軟性** | 決まった流れのみ | ユーザー指示に応じて動作変更 |
| **例** | 見積もり作成の自動化 | 営業全体プロセスの自動化 |

**重要な定義：**

複数のAIエージェントを直列に繋いだシステムは、エージェント型AIではなく、**規模の大きいAIエージェント**ととらえられます。

複数のAIエージェントを統率する別のAIエージェントを配置することで、AIエージェントを自律的に使い分けるエージェント型AIを実現できます。

### AIエージェントの実装手段

#### AIエージェント実装の本質

ここまでAIエージェントやエージェント型AIを抽象的に理解してきましたが、実際にどうやってこれを作るのか、そしてこれがどのように動くのかイメージを持てない方も多いはずです。

AIエージェントは**AIの判断をもとに自動実行するシステム**です。

つまり：
- **判断を行う**：必ずAI
- **実行を行う**：生成AIであったり、従来型のシステムであったりする

#### 実装方式の重要ポイント

AIエージェントの動きをイメージしにくい理由は、判断を行うAIと実行を行うシステムがどのように連携しているのかが分かりにくいからです。

**実際のところ：**

AIエージェント やエージェント型AIを実装する際のポイントは、この**連携システムの部分をどのように実装するか**という話に帰着します。

#### 連携システムの5つの実装方式

この連携システムの実装方式には5つのやり方があります。

---

### 実装方式1：APIの活用

既存の従来型システムとしてのクラウドサービスの多くは、API連携の機能を備えています。また、ChatGPTやDifyなど、生成AIサービスの中にもAPI連携できるものがあります。

#### APIを使った実装

```
特徴：
API連携できるシステム同士は、自分で開発したオリジナルの
システムの中で自由に連携させることができる

実装：
AIの判断とそれに応じた他のシステムの操作を
1連の処理として行う機能を実装
       ↓
それがAIエージェント
```

#### APIのメリット・デメリット

| 項目 | 詳細 |
|------|------|
| **メリット** | - 非常に基礎的な手法で実績が多い<br>- 連携できるシステムの種類が多い<br>- 開発事例も多い |
| **デメリット** | - 生成AIと他システムの連携では次に紹介するMCPの方がスタンダード化しつつある<br>- 今後MCPが主流になる可能性が高い |

---

### 実装方式2：MCP（Model Context Protocol）

#### MCPとは

MCPというのは、生成AIクラウドを提供するAnthropic社が開発した**生成AIと外部システムを接続するためのプロトコル**です。

仕組みとしてはAPIの1種とも言えますが、一般的には**従来のAPI連携を生成AI用に発展させたもの**と理解されています。

#### APIとMCPの2つの大きな違い

##### 違い1：仕様の標準化

```
従来のAPI：
- 仕様はサービス提供者が独自に決める部分が多い
- バラバラで覚えるのが大変

MCP：
- ルールとして予め定められている部分が多い
- 生成AIが処理しやすいように設計
```

##### 違い2：連携機能の動的発見

```
従来のAPI：
- 複数の機能を提供（情報登録API、検索API等）
- エンジニアが仕様書を読んで判断
- プログラムで明示的に指示する形で実装

MCP：
- 機能のラインナップが書かれたリストを取得
- その中から生成AIが利用機能を自律的に選択
```

#### MCPの現在位置と将来性

MCPは2024年の年末に登場した新しい概念ですが、AIエージェントへの期待とともに急速に発展しています。

これからますます重要になっていく技術なので、ぜひ覚えておきましょう。

#### MCPを利用したAIエージェント実装

```
理想形：すべてをノーコードで実装できるツール
現状：一部分をノーコードで開発できるツールはあるが、
      全体を成立させるには少なからず自前の開発が必要
```

#### 全機能を自前構築する場合の構成

##### 1. フロントエンド（ユーザー操作画面）

```
特徴：
- AIと直接関係ない
- 従来のフロントエンド開発の技術で実装
```

##### 2. サーバー処理（重要な部分）

```
①判断処理用の生成AI
- AIとMCPを接続するためにAIエージェント開発用の
  ライブラリを使う

②生成AI選択
- ChatGPTの場合：OpenAI Agents SDKを使用
- 利点：接続したいMCPの情報を書いておくだけで、
       ChatGPTが自律的に利用するサービスを選択・実行
```

##### 3. MCP側の準備（開発上重要）

```
用語定義：
- MCPクライアント：MCPを呼び出す機能
- MCPサーバー：実際の処理を行う機能

従来のAPI vs MCP：
従来のAPI：MCPサーバーにあたる処理の実行部分は
           外部システム側であらかじめ用意されている

MCP：まだそこまでの環境が整備されていない
     外部システムと接続するためのMCPサーバーを
     自分で構築しなければならない場合も多い
     ↓
     従来のAPIと比べて開発の難易度が高い
```

---

### MCPの3つの実装方式

MCPについて、技術的な話を少し補足しましょう。MCPの実装方式には3種類があります。

| 実装方式 | 説明 | 特徴 |
|---------|------|------|
| **方式1** | 自分のサーバー内にMCPサーバーを構築し、その中で処理を完結 | シンプル |
| **方式2** | 自分のサーバー内にMCPサーバーを構築し、そのMCPサーバーが外部のAPIを使って外部システムを操作 | 柔軟性高い |
| **方式3** | 外部にあるMCPサーバーに接続 | 実際には利用可能なサーバーが少ない |

#### 現実的な実装状況

MCPの情報を調べると、外部のシステムを操作するタイプのものが多いので、特に従来のAPIを使った開発を行ってきたエンジニアは**方式3の形をイメージ**されることが多いです。

しかし、実際には方式3で利用できるMCPサーバーはあまり存在していません。

その為、MCPを使いたい場合には、**方式1または方式2のように自分でMCPサーバーを構築することになります。**

#### MCPサーバー構築の工夫

```
1から開発する必要はない：
- WEB上にはMCPのマーケットプレイスがある
- ここでオープンソースのMCPのプログラムが公開されている
- これらを使ってMCPサーバーを構築可能

便利なツール：
- MCPサーバーのプログラムが置かれている場所などの設定を
  書くだけでMCPサーバーを立ち上げられる
  MCP開発用のライブラリやツール
```

#### MCPの課題と将来性

```
現状：
少なからず開発を伴うため、
開発が得意でない方にとっては導入のハードルが少し高い

将来性：
技術的な難しさについては、MCPの普及とともに
便利なツールがいろいろと登場して解決していくはず

推奨：MCP関連のニュースにはぜひ注目
```

### AIエージェントのノーコード実装例

#### デモンストレーションの狙い

実際に動くAIエージェントの実物を見ながら、AIエージェントがどのように動作するのか、そしてどのように実装されているのかを目で見て理解しましょう。

ここでは詳細なハンズオンは行いませんが、開発経験のない方でも理解していただけるよう、可能な限りノーコードで仕組みが分かりやすいツールを選択しています。

#### 対象プロセス：営業自動化

営業プロセスの自動化として、以下を実装します：

```
フロー：
フォームからの問合せ受領
   ↓
担当部署を割り振り
   ↓
見積もりを算出
   ↓
提案書を作成
```

#### 実装システム構成

**データ収集：** Microsoft Forms
**データ格納：** SharePoint（via PowerAutomate）
**見積もり作成：** Dify（生成AI）
**提案書作成：** Genspark（生成AI）

#### ステップ1：従来型の自動化（PowerAutomate）

```
処理内容：
- Formsの投稿をトリガー
- フォーム内容を取得
- 選択された業界を元に担当部署を決定
- SharePointのリストに追加

特徴：
- 完全にルールベースの自動化
- AIは利用していない

重要なポイント：
所属部署の選択をAIにすることもできますが、
むしろ正確性が下がって業務が混乱する可能性あり。
無理してAIを使わない判断をすることも大切
```

#### ステップ2：見積もりAIエージェント（Dify）

```
インプット準備：
- 過去の案件情報をExcelで作成
  （業務実装時はデータベース推奨：常に最新情報参照可能）

実装内容：
1. 入力された案件情報で過去案件を検索
2. 類似案件を抽出
3. ChatGPTが見積もりを算出

特徴：
- 単体で動作
- 人間がSharePointから案件情報を取得
- 手動でDifyを起動
- 出力された見積情報を手動で記録
```

#### ステップ3：提案書作成（Genspark）

```
処理内容：
- SharePointの案件情報を手動で入力
- Difyの見積情報を手動で入力
- スライドを自動生成

特徴：
- 生成されたPPTをダウンロード
- 人間が最終化
- 提案に向かう
```

#### 補足：見積もりは従来型AIも有効

見積もりのように**数値を予測する処理**は、生成AIよりも従来型のAIを使った方がチューニングしやすく、実用的な場合も多いです。

```
例：Simple ML for Sheets（Googleスプレッドシートのアドオン）
- スプレッドシート上でノーコードで機械学習が動作
- 見積もりエージェントとして利用可能
- 過去の案件情報をもとに見積金額を計算
```

### エージェント側のAIのノーコード実装

#### 発展形：完全自動化エージェント型AI

前のレクチャーで作ったAIエージェントを拡張して、提案書作成まで1連の業務を全て自動化できるエージェント型AIを作成してみましょう。

#### 実装の変更点

##### 変更1：PowerAutomateの拡張

```
新機能追加：
- SharePointへの追加後にDifyのAPIを自動呼び出し
- 見積もりエージェントを自動起動
```

##### 変更2：Difyの拡張

```
従来：AIのプロセスブロック
変更後：エージェントブロックに変更
追加：Browser Use Cloudを接続
機能：Gensparkへのアクセス、提案書スライド作成指示
```

#### 動作メカニズム

```
HTTPブロック追加：
PowerAutomate → SharePoint追加後 → Dify自動呼び出し

エージェントブロック：
Browser Use CloudとChatGPTが統合
ユーザー要求に応じてBrowser Use Cloudを使用するか判断
```

#### 実行フロー

```
フォーム投稿
   ↓
PowerAutomate実行（自動）
   ↓
SharePointに記録
   ↓
Dify API自動呼び出し
   ↓
Browser Use Cloud起動
   ↓
Gensparkで提案書自動作成
   ↓
完了
```

#### エージェント型AIの重要な特徴

```
複数機能の統合：
Difyが見積もり算出と提案書作成の2つの機能を持つ

自律的な判断：
- 見積もりをやり直すよう指示すると → 見積機能を実行
- 提案書の作成をやり直すよう指示すると → 提案書作成機能を実行
- 指示に応じてBrowser Use Cloudを使うかどうか自動判断

臨機応変な対応：
複数のAIエージェントをあらかじめ接続しておき、
ユーザー指示に応じて臨機応変に使い分ける
```

#### セキュリティの注意点

```
デモンストレーションの方式：
- Browser Use Cloudを使ってGensparkにアクセス
- わかりやすさ重視

実装上の課題：
ログイン用メールアドレスとパスワードが
Browser Use Cloud画面でそのまま見える
↓
セキュリティ的に危ない

実運用での工夫：
自前でサーバを立てるBrowser Useを使うなど対応
```

### AIエージェントを活用した業務改革事例

#### 事例紹介の目的

AIエージェント活用のまだ歴史が浅いこともあって、事例もそれほど多くはありません。

ここでは、AIエージェントの事例の中でも、特にエージェント型AIの概念を取り入れているものや、従来のシステムでは不可能だった業務プロセスを実現したものなど、これまでのレクチャーで考えて来たAIエージェント像の振り返りになる事例を紹介します。

#### 事例1：シーメンス（ドイツ）- メンテナンスサポート

**背景：**

製造現場では、機械のダウンタイムが生じるたびに多大なコストが発生します。工場では年間平均で約800時間ものダウンタイムがあり、企業経営に大きな負担を与えています。

**原因：** 熟練した労働者の不足

実際に問題が発生すると、原因の特定、マニュアルの確認、解決方法を見つけることに膨大な時間がかかり、その間機械は停止したままになってしまいます。

**解決策：** メンテナンスサポートAIエージェントの導入

```
仕組み：
- 工場の機器に関連する様々なデータを統合
- AIチャットボットがリアルタイムに対応

データ統合内容：
- マニュアル、仕様書
- エラーログ、チェックリスト
- PLCデータ

機能：
- トラブル発生時のエラーコードの意味を説明
- 必要なメンテナンス作業をガイド
```

**成果：**

| 指標 | 改善内容 |
|------|---------|
| **対応可能性** | 従来：専門の熟練者のみ → 経験少ないスタッフが自力で対応可能 |
| **時間短縮** | メンテナンス時間が従来比で**25%削減** |
| **稼働状況** | 24時間365日稼働可能 |

**重要な転換：**

従来は「適切な人を探して派遣する」という手法だったのに対し、「その場にいる作業者自身を適切な人間に変える」という新しいコンセプトを実現しました。

#### 事例2：韓国の大手企業 - 経費精算

**背景：**

大量の経費申請処理が日常的に行われている企業。定型作業の効率化手段としてRPAを導入していた。

**RPA導入の問題：**

実際には例外的なパターンが多く、RPAの基本的なルールでは処理しきれない申請が頻繁に発生。結果として人間による確認作業が減らず、確認ミスも起きやすく、期待したほどの効率化が達成できていなかった。

**解決策：** 経費精算自動チェックAIエージェント

```
フェーズ1：
- 従業員がアップロードした領収書をOCRで読み取り
- ルールベースで自動承認（ここまではRPAで実現）

フェーズ2：AIエージェント追加
- ルールベースでNGとなった領収書に対して柔軟な判断
- 過去の申請事例や承認パターンをもとに
  例外的な申請についても人間の判断に近い対応
```

**学習機能の工夫：**

```
1度承認されたパターン
   ↓
システムの自動チェックのルールに自動追加
   ↓
その後は完全に自動で処理可能
   ↓
継続的に効率化が進む
```

**成果：**

| 指標 | 改善内容 |
|------|---------|
| **自動化率** | 経費精算業務全体の**80%以上が自動化** |
| **エラー削減** | エラー率も同時に減少 |
| **業務負担** | 人間の作業は最終確認のみに |

#### 事例3：WALMART - 調達交渉

**背景：**

グローバル化が進む現在、調達業務では不確実性への対応（パンデミック、地政学リスク）が重要。小売業界では調達コスト削減とリスク管理のバランスが課題。

**解決策：** AIエージェントによる調達交渉

```
仕組み：
企業がサプライヤーに対して交渉したい条件を提示
   ↓
AIチャットのリンクをサプライヤーに送付
   ↓
サプライヤーはAIエージェントとチャットで交渉
   ↓
条件を詰めていく
```

**成果：**

| 指標 | 成果 |
|------|------|
| **合意取得率** | AIエージェントと交渉したサプライヤーの**68%から合意を獲得** |
| **コスト改善** | **1.5%のコスト改善** |
| **支払い条件** | **35日延長** |
| **サプライヤー満足度** | **4分の3が人間との交渉よりAIとの交渉を好む** |

**重要な発見：**

交渉のような複雑な対話では、むしろ感情のないAIの方が人間よりかえって話しやすい場合があるということです。

**将来の可能性：**

発注者と受注者のAIエージェント同士が交渉を行うという未来もあり得るかもしれません。

#### AIエージェント導入事例の共通点

**特徴的なポイント：**

```
❌ 単に人間の仕事をAIに置き換えているのではなく
✓ 人間だけでは実現できなかったプロセスを実現している

これが正にAIエージェントという新しい業務改革手段による
働き方の変化の本質
```

### このセクションのまとめ

#### AIエージェントの定義と特性

このセクションでは、AIエージェント、そしてその発展系であるエージェント型AIについて学びました。

| 用語 | 定義 |
|------|------|
| **AIエージェント** | AIの判断をもとにタスクを自動実行するシステム |
| **エージェント型AI** | AIエージェントや他のシステムを組み合わせて、それらを自律的に使い分けながら仕事を進めるシステム |

#### 実装のポイント

AIエージェント やエージェント型AIを構築する際のポイントは：

1. **どの業務にどんなシステムを当てはめるのか**
2. **システム間の連携をどのように実装するか**

#### 技術理解と発想の重要性

AIエージェントの実装方法については、少し難しく感じられた方もいらっしゃるかもしれません。

ただ、技術の前に重要なのは、**どんなエージェントを作るかというアイディア**です。

ぜひ本セクションで学んだ基本的な概念をもとに、皆さん自身が実現したいAIエージェントの姿を想像してみてください。
